# 扫码出水结果回报接入说明

## 业务规则

以控制板 `api/v2/scan/<设备SN>` 上报的 `scan_water` 事件判断实际出水结果。
ACK 仅反映命令受理情况，不代表出水完成。

| 事件 | 原因 | 出水状态 | 退款 |
| --- | --- | --- | --- |
| started | none | 出水中 | 不退款，等待最终结果 |
| done | target_met | 已完成 | 正常结算，不退款 |
| abort | no_flow | 异常：未出水 | 全额退回实付金额 |
| abort | flow_stall | 异常：中途断流 | 即使部分出水，也全额退回 |
| abort | timeout | 异常：出水超时 | 即使部分出水，也全额退回 |
| stopped | user_stop | 异常：主动停止 | 即使部分出水，也全额退回 |
| 未收到最终事件 30 分钟 | - | 结果超时 | 全额退回实付金额 |

不按差额退款，不追加收费。退款成功与出水结果分别记录，保留已出水量和异常原因。
正常完成以固件 `done/target_met` 为准，协议示例中的 498/500ml 不会因脉冲舍入自动判为异常。
热水的 actualMl 为固件估算值，后台标注“估算”；当前固件不能据此证明热水实际有流量。

## 消息关联与可靠性

- 平台先生成并保存出水命令 messageID，再调用 IoT 服务发布 Q74。
- QoS 1 订阅 `api/v2/scan/+`，数据库收件箱持久化成功后才完成 MQTT 回调。
- MQTT 使用持久会话；能否在平台断线期间保留消息，仍取决于 Broker 的会话和队列保留配置。
- 结果处理独立于 MQTT 回调，每两秒轮询持久化收件箱。数据库失败保留待处理记录。
- 设备 SN、命令 messageID、水类型、目标水量必须与已支付订单匹配。无法关联的回报保留等待，不通过“设备最新订单”猜测归属。
- started 可以缺失；最终事件可直接完成订单。重复最终事件不重复结算；完成后迟到的 started 不覆盖终态。
- 同一命令不同的最终结果进入冲突审计，不自动修改既有结算。
- START 的应用层发送次数为一次，ACK 未确认时等待结果，不为获得 ACK 再执行一轮出水。
- ACK 超时、设备离线或缺少结果时，订单保持等待最终结果。自命令下发起满 30 分钟仍未收到 done、abort 或 stopped，订单标记“结果超时”并进入全额退款队列。
- 30 分钟超时退款后，迟到的最终回报仍会保存为实际设备结果，但不会撤销或重复已经发起的退款。
- 自动退款选择有最终 abort/stopped 回报的已支付异常订单，或最终结果满 30 分钟超时的订单；退款请求失败后使用同一退款单号重试，防止重复退款。

## 主动停止

`POST /api/v1/water/scan-orders/{orderNo}/stop` 为已授权管理员或订单所属客户发起 STOP，
预先保存独立 stopMessageId。控制板可按协议返回 STOP 的 messageID，系统仍能关联原订单。
若设备已经接收后续订单，则不能通过旧订单停止当前出水。未知的外部 STOP messageID 不推测关联。
本次提供后台接口，未新增小程序停止按钮。

## 数据与部署

数据库迁移：`sql/add_scan_water_result.sql`，支持重复执行。
新增 `water_scan_inbox` 表及订单命令关联、实际水量、估算标志、结果类型、结果原因、结果接收时间字段。
原有历史订单和退款记录不回写；缺少设备回报的历史实际水量保持未知，不能当作真实出水量统计。
订单列表新增设备回报水量、原因、结果接收时间及出水中、已完成、等待结果、结果待核实筛选。

## 验证

使用独立 MySQL 测试数据库和模拟微信支付客户端回放正常完成、未出水、部分出水、
主动停止、热水估算、重复与乱序回报、身份参数不符、离线补报、退款失败重试及并发退款。
验证过程不得向真实设备发送 START/STOP，也不得向真实订单发起测试退款。
