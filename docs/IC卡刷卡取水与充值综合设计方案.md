# IC 卡刷卡取水与充值综合设计方案

## 1. 文档目的

本文定义直饮水平台接入 IC 卡刷卡取水及线下充值功能的业务边界、技术架构、资金处理和实施路径。

本方案适用于当前直饮水平台、现有饮水机控制板和 MQTT 出水结果回报机制。第一期以 M1 卡为载体，平台账户余额为唯一资金依据；卡片不保存余额，也不负责离线扣费。

## 2. 核心原则

1. **平台账户余额为准。** 充值、扣费、退款和人工调账均以平台钱包流水为准，卡片不保存余额。
2. **卡片仅用于身份识别。** 卡片承载卡号与必要校验信息，不能将卡内余额作为结算依据。
3. **刷卡后先建立取水会话锁。** 平台锁定卡片和设备，控制板亮起刷卡指示灯；用户按实体取水按钮后才开始出水。
4. **所有资金变化均可审计。** 不允许直接修改钱包余额而不产生对应的不可变更流水。
5. **按实际出水量结算。** 控制板记录最终实际出水量，平台按会话开始时锁定的水价计算并扣除余额。
6. **第一期在线运行。** 设备刷卡授权、会话锁定、扣费和解锁均需要与平台实时通信；离线设备不允许确认扣费。

## 3. 适用范围与边界

### 3.1 第一期开通能力

- M1 卡发卡、绑定、挂失、解绑和换卡。
- 饮水机刷卡身份识别、余额校验、卡片/设备会话锁定和按量结算。
- 后台平台钱包余额、卡片取水会话、充值与退款流水。
- 线下充值：USB 读卡器读取卡片身份，平台工作人员完成充值。
- 用户再次按键结束出水后，按控制板最终计量水量扣费并释放会话锁。
- 无出水、设备异常或无最终结果时释放会话锁；未获得可信最终计量结果时不扣费。
- 管理员人工退款、人工调账、风控限制和审计查询。

### 3.2 不在第一期范围内

- 卡片离线余额、离线消费和离线充值。
- 脱机设备间余额同步。
- 将 M1 卡作为高安全金融储值卡使用。
- 设备离线情况下继续取水或离线结算。

### 4.1 控制板读卡模块

- 推荐使用 **PN532**：协议成熟，可通过 UART、I2C 或 SPI 与控制板连接，稳定性优于多数低成本读卡方案。
- RC522 可用于低成本原型，但在抗干扰、兼容性和现场稳定性方面应进行专项验证。
- 控制板读取 M1 卡 UID 和指定扇区内的 `cardNo` 后，向平台发起刷卡授权。

### 4.2 线下充值读卡器与桥接程序

线下充值电脑使用 USB 读卡器，例如 ACR122U。浏览器一般不能直接稳定访问 USB/NFC 读卡器，因此需要一个轻量本地读卡桥接程序。

桥接程序职责：

1. 与 USB 读卡器通信，读取 UID 和卡内 `cardNo`。
2. 向已登录的后台网页提供本机回环地址接口或 WebSocket 事件。
3. 不保存平台余额、充值金额、平台登录令牌或完整用户数据。
4. 仅将卡片识别结果交给后台，由平台完成用户识别和充值入账。

## 5. 卡片设计

### 5.1 M1 卡内数据

建议使用一个指定的应用扇区保存以下信息：

| 字段 | 说明 |
| --- | --- |
| `cardNo` | 平台随机生成的卡号，非连续、不可推测 |
| `version` | 卡片数据格式版本，用于后续升级 |
| `issuedAt` | 发卡时间或发卡批次标识 |
| `checkValue` | 卡片校验值，用于识别空白卡或异常数据 |

卡内不得保存：平台钱包余额、累计消费金额、退款金额、后台账号密码、支付密钥或 API Key。

### 5.2 绑定规则

- 一张有效卡只绑定一个平台用户。
- 一个用户可按运营规则绑定多张卡，但必须明确主卡、备用卡或历史卡状态。
- 换卡时：旧卡立即挂失或停用；新卡绑定同一钱包账户；余额无需转写到卡内。
- 挂失后，任何设备刷到该卡均拒绝取水。

### 5.3 M1 卡安全边界

仅使用 UID 作为身份依据存在复制卡风险。第一期至少应使用“**UID + 随机 cardNo + 扇区认证**”组合。

- 为应用扇区配置独立 Key A / Key B，禁止使用默认密钥。
- 不同发卡批次或卡片建议采用密钥分散策略。
- 平台以 UID、`cardNo`、卡状态和用户状态共同校验。
- 设置单笔限额、日限额、短时间连续刷卡限制和异常设备告警。
- 卡丢失后立即挂失；挂失操作实时同步至平台。

M1 的 Crypto1 不适合承载高价值金融安全。若未来卡量、余额规模或安全要求明显提高，应升级为 DESFire 或 CPU 卡。

## 6. 刷卡取水业务流程

### 6.1 刷卡授权与会话锁定

```text
用户刷卡
  ↓
设备读取 UID + cardNo
  ↓
设备请求平台卡片授权
  ↓
平台校验卡状态、用户状态、设备权限、余额和风控规则
  ↓
平台创建唯一刷卡取水会话，锁定该卡和该设备
  ↓
平台返回 sessionId、水价快照、最大允许出水量和会话有效期
  ↓
控制板亮起“刷卡已授权”指示灯，等待用户按取水按钮
  ↓
用户按下取水按钮后，控制板开启对应水路并记录实际出水量
  ↓
用户再次按下取水按钮，控制板关闭水路并上报最终实际出水量
```

### 6.2 最大出水量保护

卡片与设备在会话未结束前均不可被其他刷卡会话占用。平台应同时保存数据库会话记录和带过期时间的分布式锁，避免同一张卡或同一台设备被并发使用。

本模式不预选固定水量，也不在刷卡时冻结资金。因此平台必须在授权时按当前余额和水价计算控制板可出水上限，防止实际出水金额超过余额。

```text
最大允许出水量（ml） = min(
  平台配置的单次最大水量，
  floor(可用余额（分） × 1000 ÷ 当前水价（分/升）)
)
```

- 水价在刷卡授权成功时写入会话快照，取水过程中即使后台调整价格也不影响本次结算。
- 冷水、热水应分别计算最大允许出水量；控制板须按用户选择的水路使用对应水价上限。
- 控制板达到最大允许出水量时必须自动关闭水路并上报正常结束结果。
- 如果可用余额不足以支持平台设置的最小出水量，平台拒绝建立会话，刷卡指示灯不亮。

### 6.3 出水结算与解锁

| 控制板最终结果 | 平台订单状态 | 钱包处理 | 卡片与设备 |
| --- | --- | --- | --- |
| 用户再次按键结束，或达到最大水量 | 已完成 | 按最终 `actualMl` 与水价快照扣费 | 扣费成功后解锁 |
| 未出水，`actualMl = 0` | 已取消 | 不扣费 | 立即解锁 |
| 流量异常但有可信 `actualMl` | 异常已结算 | 按实际 `actualMl` 扣费，并记录异常原因 | 扣费后解锁 |
| 流量异常且无可信计量 | 异常未结算 | 不扣费 | 立即解锁 |
| 会话过期且未开始出水 | 已过期 | 不扣费 | 自动解锁 |
| 出水已开始但未收到最终结果 | 待人工核实 | 暂不扣费，触发告警 | 保持短暂保护锁，超时后安全解锁 |

结算金额使用水价快照计算：`金额（分） = roundHalfUp(actualMl × 单价（分/升） ÷ 1000)`。计量精度、最小计费量和舍入规则应作为设备型号配置项，并在订单中保存最终采用的规则。

用户主动按键结束属于正常结束，最终回报不得复用扫码取水的 `stopped` 异常语义。建议卡取水回报统一使用 `event=done`、`reason=user_stop` 或 `reason=max_volume_reached`；平台据此按实际水量结算。

### 6.4 控制板交互要求

1. 控制板读取卡片后，必须先取得平台返回的 `sessionId` 才能点亮刷卡指示灯。
2. 刷卡指示灯亮起仅表示“已授权、等待按键”，此时不得开启水阀。
3. 第一次按取水按钮：控制板上报 `started`，开启水阀并从零开始累计本次 `actualMl`。
4. 第二次按同一取水按钮：控制板先关闭水阀，再上报包含 `sessionId`、水路类型、最终 `actualMl` 的结束结果。
5. 平台完成扣费或决定不扣费后，返回结算确认；控制板熄灭刷卡指示灯并清除本地会话。
6. 控制板必须在网络断开、会话超时、卡被平台挂失或达到最大水量时强制关闭水阀。

### 6.5 幂等与关联要求

- 每个刷卡会话生成唯一 `sessionId`、`orderNo` 和 `commandMessageId`。
- 控制板必须在 `started`、结束结果和异常结果中复用同一个 `sessionId` 与 `commandMessageId`。
- 平台按照设备 SN、`sessionId`、`commandMessageId` 和事件类型处理幂等，重复消息不得重复扣费或重复解锁。
- 设备最终结果可沿用现有主题 `api/v2/scan/<device_id>`，但载荷需增加 `sessionId`、水路类型、最终 `actualMl` 和正常结束原因。

## 7. 线下充值设计

### 7.1 充值流程

```text
工作人员打开后台“线下卡充值”页面
  ↓
将卡放入 USB 读卡器
  ↓
桥接程序读取 UID + cardNo 并传递给浏览器
  ↓
后台调用平台查询卡片、绑定用户和当前余额
  ↓
工作人员输入充值金额、收款方式和备注
  ↓
平台创建充值订单、钱包流水并增加可用余额
  ↓
页面展示充值成功与充值后余额
```

### 7.2 充值约束

- 充值操作只能由具有钱包充值权限的后台角色执行。
- 必填字段：卡号、用户、金额、收款方式、操作人。
- 推荐可选字段：收款凭证编号、备注、线下支付凭据附件。
- 充值成功后余额即时生效，不需要向卡内写入余额。
- 重复提交通过充值订单号和幂等键防止重复入账。
- 充值撤销不得删除原流水，应创建反向调账流水并保留审批记录。

## 8. 数据模型

### 8.1 `ic_card`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `card_no` | 平台卡号，唯一 |
| `uid_hash` | 卡 UID 哈希或脱敏索引 |
| `customer_id` | 绑定用户 |
| `status` | ACTIVE、LOST、DISABLED、REPLACED |
| `issued_at` | 发卡时间 |
| `lost_at` | 挂失时间 |
| `replaced_by_card_id` | 换卡关联 |

### 8.2 `wallet_account`

| 字段 | 说明 |
| --- | --- |
| `customer_id` | 用户，唯一 |
| `available_amount` | 可用余额，单位分 |
| `frozen_amount` | 预留字段；本刷卡按量方案不在授权时冻结资金 |
| `version` | 乐观锁版本 |

### 8.3 `wallet_ledger`

| 字段 | 说明 |
| --- | --- |
| `ledger_no` | 唯一流水号 |
| `customer_id` | 钱包用户 |
| `biz_type` | RECHARGE、CONSUME、REFUND、ADJUST；预留 FREEZE、UNFREEZE |
| `amount` | 本次变动金额，单位分 |
| `balance_after` | 变动后余额快照 |
| `related_order_no` | 关联充值单或取水单 |
| `operator_id` | 操作人或系统任务标识 |
| `created_at` | 创建时间 |

### 8.4 取水订单扩展

复用现有 `water_dispense_order`，新增或明确以下字段：

- `payment_provider`：增加 `WALLET_CARD`。
- `session_id`：刷卡取水会话标识，唯一且不可复用。
- `card_id`、`card_no_masked`：关联卡片并用于展示。
- `price_snapshot_fen_per_litre`：授权时固化的水价。
- `max_allowed_ml`：平台根据余额和限额计算的最大允许出水量。
- `actual_ml`、`settlement_amount`、`settled_at`：最终计量、实际扣费金额和结算时间。
- `command_message_id`、`result_event`、`result_reason`：继续复用现有结果关联字段。

### 8.5 `card_water_session`

该表用于卡片与设备互斥锁定，不能仅依赖控制板内存状态。

| 字段 | 说明 |
| --- | --- |
| `session_id` | 会话唯一标识 |
| `card_id`、`device_id` | 被锁定的卡片和设备 |
| `status` | AUTHORIZED、DISPENSING、SETTLING、CLOSED、EXPIRED、REVIEW |
| `water_type` | 冷水或热水 |
| `price_snapshot_fen_per_litre` | 结算水价快照 |
| `max_allowed_ml` | 控制板必须执行的最高水量 |
| `actual_ml` | 控制板最终上报水量 |
| `expires_at` | 未开始出水的授权过期时间 |
| `locked_at`、`started_at`、`ended_at` | 会话关键时间 |

## 9. 刷卡会话与钱包状态机

```text
可用余额
  │ 刷卡授权通过
  ▼
卡片与设备锁定（AUTHORIZED）
  ├── 首次按键 ────────────▶ 出水中（DISPENSING）
  ├── 未按键超时 ──────────▶ 释放卡片与设备锁，不扣费
  └── 取消 / 刷卡失效 ──────▶ 释放卡片与设备锁，不扣费

出水中（DISPENSING）
  ├── 二次按键 / 达到上限 ──▶ 按 actualMl 扣费，释放卡片与设备锁
  ├── 无可信计量异常 ───────▶ 不扣费，释放卡片与设备锁
  ├── 有可信计量异常 ───────▶ 按 actualMl 扣费，释放卡片与设备锁
  └── 未收到最终结果 ───────▶ 进入人工核实并告警，安全解锁

已消费订单
  └── 管理员人工退款 ───────▶ 新增 REFUND 流水恢复平台余额
```

任何状态变更必须采用事务、行锁或乐观锁，保证并发刷卡、设备重复回报和退款任务同时到达时不会重复扣费或重复恢复余额。

## 10. 后台功能与权限

| 功能 | 建议权限 |
| --- | --- |
| 卡片查询 | `IC_CARD_VIEW` |
| 发卡、绑定、换卡 | `IC_CARD_MANAGE` |
| 挂失、停用 | `IC_CARD_LOSS_REPORT` |
| 钱包查询 | `WALLET_VIEW` |
| 线下充值 | `WALLET_RECHARGE` |
| 人工调账 | `WALLET_ADJUST` |
| 卡取水退款 | `WALLET_REFUND` |
| 卡片与钱包审计 | `WALLET_AUDIT_VIEW` |

人工调账、人工退款、批量挂失应记录操作人、操作时间、前后金额、原因、关联单号和审批记录。

## 11. 风控规则

- 卡状态必须为 ACTIVE，且绑定用户未禁用。
- 余额必须达到平台设置的最小可取水金额；授权时计算最大允许出水量并由控制板强制执行。
- 每卡设置单笔金额、单日金额和单日次数限制。
- 限制同一卡片在短时间内跨设备连续刷卡。
- 设备可配置允许刷卡用户范围或特定客户范围。
- 卡片或设备已被有效会话锁定时，不允许创建第二个刷卡会话。
- 设备离线、平台不可达或订单仍处于未结算状态时，不允许创建新的刷卡取水会话。
- 连续出现卡认证失败、卡号不匹配、余额不足或异常退款时触发告警。

## 12. 实施阶段

### 阶段一：平台钱包与卡管理

1. 创建卡片、钱包账户、钱包流水和线下充值订单表。
2. 实现发卡、绑定、挂失、换卡、钱包查询和线下充值后台页面。
3. 建立权限、操作审计和资金流水校验。

### 阶段二：控制板刷卡授权

1. 选型并接入 PN532 或经验证的读卡模块。
2. 实现 UID、`cardNo` 读取及扇区认证。
3. 定义卡片授权请求、授权结果和拒绝原因协议。
4. 设备通过平台授权后锁定卡片与设备，点亮刷卡指示灯，等待实体取水按钮。

### 阶段三：订单结算与退款

1. 增加刷卡取水会话表、设备/卡片互斥锁和按量结算字段。
2. 将 `api/v2/scan/<device_id>` 最终结果接入按实际水量扣费状态机。
3. 实现二次按键结束、最大水量自动停止、会话过期与无可信计量不扣费。
4. 支持管理员人工退款和完整流水审计。

### 阶段四：线下读卡桥接程序

1. 实现 Windows 桌面桥接程序或本地服务。
2. 对接 ACR122U 等 USB 读卡器。
3. 通过本机回环接口与后台充值页面通信。
4. 完成读卡器断开、读卡失败、重复刷卡和异常卡提示。

## 13. 验收场景

1. 正常刷卡后卡片与设备均被锁定，刷卡指示灯亮起；首次按键开始出水，二次按键结束出水并按实际水量扣费。
2. 余额不足、挂失卡、停用卡和未绑定卡均被拒绝。
3. 达到平台下发的最大允许出水量时，控制板自动关闭水阀、上报最终水量并完成扣费与解锁。
4. 未出水、无可信计量异常和未开始会话超时均不扣费，并解除卡片和设备锁。
5. 出水中未收到最终结果进入人工核实；迟到结果和重复 MQTT 消息不得重复结算。
6. 线下充值一次入账一次；重复点击或网络重试不得重复增加余额。
7. 换卡后旧卡不能使用，新卡可直接使用原钱包余额。
8. 人工退款、调账、挂失和充值均可在审计日志追溯。

## 14. 结论

本方案可以与当前平台融合，且不改变现有扫码取水的核心逻辑。通过把卡片定位为身份凭证、把余额和资金操作集中到平台钱包，可避免卡内余额不同步、退款难以追踪和线下数据不一致的问题。

第一期使用 M1 卡可满足常规运营需求，但必须实施扇区认证、随机卡号、平台实时校验、挂失和限额。涉及较大资金规模或更高安全要求时，应规划升级至 DESFire 或 CPU 卡。
